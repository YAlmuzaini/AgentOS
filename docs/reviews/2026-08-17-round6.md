## 1. Is the goal loop bounded on every path?

Yes. Every turn outcome now advances a monotonic counter:

| Turn outcome | Counter advanced | Ceiling | Spends |
|---|---|---|---|
| Roster read throws | `stuckCount` via `settleTurn` (`goal-orchestrator.ts:116`) | `stuckThreshold` | no |
| Decision failed (non-unavailable) | `stuckCount` (`:201`) | `stuckThreshold` | yes, one call |
| Decision unavailable | `goal_decisions` streak (`:175`) | `MAX_UNAVAILABLE_TURNS` = 20 | no (see L-4) |
| Dispatch reached | `iterations` via `reserveIteration` (`:355`) | `MAX_ITERATIONS` = 100 + rails | yes |
| No eligible agent / no next agent | immediate `stop()` | — | no |
| Parked on inbox | reaper → `abandonAfterReap` | — | already spent |

The `unavailable` turn is the only outcome that advances neither `stuckCount` nor `iterations`, and it is exactly the one the new streak covers. Adversarial sequencing does not escape: an `unavailable`→`failed` alternation resets the streak but `stuckCount` is monotonic (only progress clears it, `goals.service.ts:239`), so it converges at `stuckThreshold`. An `unavailable`→`success` alternation converges on `iterations`. No sequence of turn outcomes is unbounded.

`checkRails` still runs first on every turn (`:85`), so spend and time rails fire even on a goal that spends 5 hours waiting.

Re-queue chain confirmed live: `maintenance.service.ts:76` → `recoverStalledGoals` → `updatedAt` refreshed each wait turn by `appendProgress` → 15-min grace → 20 turns ≈ 5 h. Matches `DEPLOY.md`.

## 2. H-1 remedies, adversarially

**(1) Bound of its own — holds.** `consecutiveUnavailableDecisions` (`goals.service.ts:170-183`) reads `goal_decisions` scoped by `goalId`, `desc(createdAt)`, `limit(MAX+1)`, backed by `goal_decisions_goal_created_idx`. `status` is plain `text` with no enum/check (`company.ts:81`), so `"unavailable"` inserts without a migration — verified, this was the obvious way for the fix to fail silently and it does not.

- *Can an unavailable attempt fail to be audited?* The audit is inside the evaluator's `catch` and is `await`ed before the rethrow (`goal-evaluator.ts:162-164`), so the orchestrator's read at `:175` always sees the current attempt. If the insert itself throws, the DB error replaces `LocalDecisionUnavailableError`, the orchestrator takes the generic branch, and `stuckCount` advances instead — fails to the *tighter* rail, not to no rail. Good.
- *Non-routed evaluator?* `GOAL_EVALUATOR` binds `RoutedGoalEvaluator` unconditionally (`goals.module.ts:22`). Only tests override it. No production path throws `LocalDecisionUnavailableError` from outside the audited `try` — `local.status()` swallows everything (`local-runner.ts:126`), and `renderDecisionInput` is pure.
- *Can the streak be reset by something that is not evidence the worker answered?* Yes, in one case, and it is benign: a `failed` row is written when the worker was never reached at all (ECONNREFUSED, DNS, `LOCAL_RUNNER_URL` unset — all `TypeError`, not `LocalRunnerHttpError`). That resets the streak. But the same turn advances `stuckCount`, so the goal still converges. See L-1 for the cosmetic consequence.

**(2) Abort widened — holds, with 10 s of headroom.** Control plane: `min(90_000 + 30_000, 180_000)` = 120 s (`local-runner.ts:394`). Worker worst case: 20 s queue (`main.ts:335`) + 90 s decision (`decision.ts:28`) = 110 s. Confirmed the 90 s timer starts *after* the slot is acquired (`main.ts:96` → `runDecision`), so the two do not overlap. See L-4.

**(3) Classify on status — holds.** `call()` throws `LocalRunnerHttpError` with `status`/`body` (`:445`); `decide()` matches `status === 503` only (`:404`). The `/\b503\b/` regex is gone. `status === 503` for a non-availability condition: the worker emits 503 from exactly two places, both capacity/drain (`main.ts:98`, `:197`). A fronting proxy's 503 is still an availability condition. Not reachable for a broken evaluator — a worker-side decision failure is a 500 and now correctly lands on the stuck rail.

**(4) Docs — corrected.** `DEPLOY.md:320-334` states the 20-turn bound, "roughly five hours", "not sent to the cloud", and the residual kill-mid-decision billing caveat. `PROGRESS.md:203-217` now says the cap under-reports on *every* goal and that what is bounded is the count (`stuckThreshold` / `MAX_UNAVAILABLE_TURNS`), not the money. Both accurate.

## 3. Findings

### Critical

### Medium

**M-1 — the stop reason instructs an action the product does not have.** `goal-orchestrator.ts:180-183`; `goals.service.ts:125-133`; `goals.controller.ts:59`; `goal-detail-parts.tsx:348`

The new stop text ends "Start or undrain the worker and **re-activate the goal**." There is no such affordance. `resume()` throws unless `status === "paused"` (`goals.service.ts:127`); the only other transition into `active` is `approveDod`, which refuses a goal already approved (`:95`). The UI renders Resume only for `paused` (`goal-detail-parts.tsx:348`). A goal in `stopped-stuck` is terminal.

Consequence: a worker outage longer than ~5 h permanently ends every local goal. The operator's only recovery is delete-and-recreate, which discards the progress log, the ticked checklist, and the accumulated `spendUsd` — i.e. the next run re-spends the whole cap from zero. That is a worse outcome than the unbounded loop for a *short* outage, and the message actively misdirects.

**Blocks unattended use: no.** It fails closed and pushes. But it makes the documented recovery path for this rail unreachable, which is the same species of defect as the previous round's M-1 (text asserting what the code does not do).

### Low

**L-1 — "unreachable" is documented as unavailable and classified as failed.** `local-runner.ts:34-36` vs `:398-415`

The class docstring says the error covers "busy, draining, **or unreachable**". A dead worker (ECONNREFUSED / DNS / unset URL) produces a `TypeError` from `fetch`, which is neither `LocalRunnerHttpError` nor an abort, so it is rethrown raw → audited `failed` → stuck rail → the goal eventually stops with *"no progress across 19 iterations"*. That is precisely the wrong sentence this whole design exists to eliminate; it just now applies to the down case instead of the busy case. Bounded and non-spending, and it does surface in the briefing as "Goal decision failed", so the operator is not blind. Cosmetic-plus.

**L-2 — the "pinned to local" clause in the stop reason is unconditional.** `goal-orchestrator.ts:181-182`

An `auto` goal can reach the ceiling: `local.status().ready` is `!draining && inUse < limit` (`capacity.ts:27`), so a health check that lands in a free window followed by a `/decisions` that lands in a full one yields `unavailable` on an `auto` goal. Sustained 20-in-a-row needs a persistent flap and is unlikely, but the message would then assert something false about the goal's routing. Guard the clause on `runnerPreference === "local"`.

**L-3 — the two joints of the new bound are untested.** `apps/api/test/goals.spec.ts:398, 468`; `apps/api/test/goal-evaluator-routing.spec.ts`

Both goal tests inject a fake `GoalEvaluator` that throws `LocalDecisionUnavailableError` directly and hand-seed the `goal_decisions` rows. Nothing exercises (a) `LocalVmRunner.decide` mapping HTTP 503 → `LocalDecisionUnavailableError`, or (b) `RoutedGoalEvaluator` writing `status: "unavailable"` rather than `"failed"`. The entire rail hangs on those two lines. Given the previous round's test asserted the *opposite* of the intended behaviour, this is worth closing.

**L-4 — the 10 s margin absorbs everything outside the two constants.** `local-runner.ts:70`, `:394`; `decision.ts:32-36`

120 s budget vs 110 s worst case leaves 10 s for TCP connect, `readJson`, `startCredentialProxy`, and the response write — all of which sit *outside* both timers. `DEPLOY.md:331` claims flatly that "a decision the worker actually ran is not discarded as 'busy'". Nearly true, not strictly. Also: `DECISION_QUEUE_ALLOWANCE_MS` and `DECISION_QUEUE_WAIT_MS` live in two deployables with only a comment binding them (`local-runner.ts:60-69`) — no shared constant, no runtime assertion.

**L-5 — two orphaned docstrings.** `goal-rails.ts:64-71` (the "absolute maximum number of specialists" block now attaches to `MAX_UNAVAILABLE_TURNS`; `MAX_ITERATIONS` at `:86` has none); `goals.service.ts:295-311` (the long `remove` docstring now sits above `exists`).
