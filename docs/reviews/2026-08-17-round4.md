## Medium

**M-A — the `preflight_checks` dedupe never matches; M2 is unfixed.** `apps/api/src/capabilities/preflight.service.ts:259-262`

`JSON.stringify(latest.findings) === JSON.stringify(report.findings)` compares a `jsonb` round-trip against a freshly constructed object. `findings` is `jsonb` (`packages/db/src/schema/company.ts:47`; migration `0025`), and Postgres `jsonb` does not preserve object key order — it normalizes keys sorted by length then bytes. A row read back orders them `code, action, message, severity, subjectId, subjectType`; `finding()` (`:306-308`) builds `code, severity, message, subjectType, subjectId, action`. The two strings can never be equal, so `same` is always `false` and the `else` branch inserts on every call.

Repro: leave a required slot unresolved, open `/company-setup`, let TanStack Query refetch on focus N times → `select count(*) from preflight_checks` = N, and the briefing's `failures` list (`briefing.service.ts`, `failedPreflights`) shows N identical "project failed preflight" entries. Exactly the symptom M2 named. No test covers the dedupe — `grep preflightChecks apps/api/test/*.spec.ts` is empty, and the harness runs real Postgres on :5433, so a test would have caught it.

Blocks unattended use: no spend and no wrong decision, but it defeats the one screen meant to be read unattended, and grows the table without bound. Fix: canonicalize before comparing (sorted keys), or store a findings hash column and use a unique index + `onConflictDoUpdate`.

**M-B — evaluator spend is invisible to the spend rail, and the C1 fix leans on it.** `apps/api/src/goals/goal-evaluator.ts:145, 156`

`goal_decisions` records backend, provider, model, `durationMs` — no cost. `goalLog.recordSpend` is only ever called with a *session* cost (`goal-orchestrator.ts:363`, `session-resumer.ts:135`). So every turn's metered evaluator call — `claude-opus-5`, `effort: "high"`, up to 12k spec + 12k progress log — is absent from `goals.spendUsd` and therefore invisible to `checkRails`. The C1 fix makes up to `stuckThreshold` (default 19) of those calls the *convergence mechanism* for a persistent failure, so the worst case is 19 unbilled-to-the-goal opus calls on a goal that ends stopped. `PRODUCT.md` sacred path: "the number that matters is the Anthropic bill, not the session row."

Blocks unattended use: no — bounded by count, small dollars. But the cap under-reports the bill on *every* goal, not just failing ones.

**M-C — a merely-busy local worker is charged to the stuck rail, and the new DEPLOY text says otherwise.** `apps/api/src/runner/local-runner.ts:338`, `apps/local-runner/src/capacity.ts:31-47`, `DEPLOY.md:312-313`

With `runnerPreference: "local"`, `RoutedGoalEvaluator` always picks the local backend (`goal-evaluator.ts:102-103`) — no readiness check, by design. The worker's `/decisions` route shares one `CapacityGate` with specialist sessions (`main.ts:35, 88-99`) and `acquire()` waits indefinitely with no server-side deadline. The control plane aborts at `min(timeoutMs + 5_000, 125_000)` = 95s. That abort throws into the *new* catch at `goal-orchestrator.ts:155`, which books it as a turn without progress. Nineteen such turns and the goal stops with `no progress across 19 iterations` — the wrong reason for "the worker was busy". Default `LOCAL_RUNNER_MAX_CONCURRENCY=2` against a 120-minute session cap makes saturation realistic once a task schedule and a goal overlap.

`DEPLOY.md:313` promises "an explicit `local` request **queues at the worker** FIFO, because local means local." True of the worker, false of the caller — which gives up after 95 seconds. Whichever side is intended, doc and behavior disagree.

Blocks unattended use: yes, partially — goals die silently with a misleading reason on a saturated explicit-local worker. Either bound the wait at the worker and return 503 with a retryable signal, or make a queue-timeout distinguishable from a decision failure so it does not advance the stuck counter.
