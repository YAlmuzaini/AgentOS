## High

**H-1 — a goal can be re-queued for ever on the "worker unavailable" path, with no rail, no counter, and no notification.** `apps/api/src/goals/goal-orchestrator.ts:162-172`; `apps/api/src/runner/local-runner.ts:364, 370`; `apps/api/src/goals/goal-continuity.ts:50-107`

The busy catch returns `false` before `settleTurn`. Nothing advances: not `stuckCount` (only `recordProgress` moves it, `goals.service.ts:206`), not `iterations` (only `reserveIteration`, never reached), not `spendUsd`. `runIteration` enqueues no successor. `appendProgress` sets `updatedAt = now` (`goal-log.service.ts:47`), so 15 minutes later `recoverStalledGoals` matches the goal again (`goal-continuity.ts:65`) and re-queues it. Repeat for ever.

The only rail that can still fire is time — `checkRails` at `goal-orchestrator.ts:85` runs before the evaluator. `maxDurationMinutes` defaults to `null` and, unlike `spendCapUsd`, requires **no acknowledgement** (`packages/shared/src/contracts/goal.ts:35 vs :33-48`). So the unbounded case is the *default* goal shape, not an exotic one.

Four reachable triggers, one of which spends:

1. **Drain.** `capacity.acquire` returns `null` immediately when draining (`capacity.ts:32`), worker answers 503 (`main.ts:98-105`). An operator draining the worker for maintenance leaves every local goal spinning every 15 minutes indefinitely. Explicit-`local` *sessions* get a clear hard failure (`runner-router.ts:113`); decisions get a silent loop.
2. **Sustained capacity.** Default `maxConcurrency` against a 120-minute session cap. Same loop.
3. **Abort-window race — this one spends.** The control plane aborts at `min(timeoutMs + 5_000, 125_000)` = **95s** (`local-runner.ts:364`) with `timeoutMs: 90_000` (`goal-evaluator.ts:120`). The worker may burn up to **20s** queueing before it even starts a decision that is itself allowed **90s** (`decision.ts:28`) — a 110s worst case. In the 95–110s window the control plane's own abort fires, `isAbort` (`local-runner.ts:42-44, 370`) classifies it as unavailable, and the goal books it as "nothing was spent" — while the worker is running a real `claude-opus-5` call that bills the subscription, or metered API if the worker holds an `ANTHROPIC_API_KEY` (`decision.ts:69`). Every 15-minute pass repeats it. The abort budget was never widened to cover the queue wait the same commit introduced.
4. **Regex misclassification.** `/\b503\b/.test(message)` (`local-runner.ts:370`) runs over `local runner /decisions: ${status} ${await response.text()}` (`:406`). Any worker **500** whose body text contains `503` — the worker returns `String(error)` verbatim (`main.ts:40`), and an upstream Anthropic overload surfaces as exactly that — is read as "busy". A permanently broken evaluator then loops for ever instead of converging on the stuck rail, making a paid call each pass.

Reproduction for (1), no live model needed: create a goal with `runnerPreference: "local"`, `maxDurationMinutes: null`, approve the DoD, `POST /drain {draining:true}` on the worker. Every maintenance pass logs "the local worker was busy", writes a `goal_decisions` row, and changes nothing else. The goal never stops and never pushes.

The existing test **asserts this behaviour** rather than catching it: `apps/api/test/goals.spec.ts:397-437` runs four busy turns and requires `stuckCount === 0`, `iterations === 0`, status `active`. It proves there is no bound.

**Blocks unattended use: yes.** "Goals have rails" is one of the five non-negotiable properties (`PRODUCT.md:39`). On this path there is no rail at all unless the operator happened to set a duration, and trigger (3) puts real money behind it while the log says nothing was spent.

## Low

**L-1 — `canonicalFindings` is order-sensitive over arrays built from unordered queries.** `preflight.service.ts:321`; `capability.service.ts:74, 35-38`

The canonical form fixes *key* order but preserves *array* order, and the findings array order derives from `select().from(agents)` and `select().from(projectResourceSlots)` with no `ORDER BY`. Under pure polling — the case M-A was about — heap order is stable and the dedupe holds. After any `UPDATE` rewrites a tuple to the end of the heap, order can change while the finding *set* does not, and the dedupe misses once. Bounded and self-limiting; a `.sort()` on the canonical tuples before stringify closes it. Does not block.

**L-2 — an unavailable worker is audited as a failed decision.** `goal-evaluator.ts:155-159`. The catch calls `audit(..., "failed", "LocalDecisionUnavailableError")` before rethrowing, so `goal_decisions` records a failure and the briefing renders "Goal decision failed" (`briefing.service.ts:32`) for the one case the fix insists is not a failure. Useful side effect: it is currently the *only* operator-visible signal of the H-1 loop, inside a 24h window. Also one row per 15 minutes for ever on that loop. Does not block on its own.

**L-3 — `PreflightService.run` never asserts the project exists.** `preflight.service.ts:53`. Unlike every sibling service it skips `projects.require`. A well-formed but unknown `projectId` on `GET .../preflight` builds a report and then attempts an insert against the FK. Operator-only route, cosmetic. Does not block.

**L-4 — dead imports.** `goals.service.ts:18` imports `isNull`, `lt`, `or`; none are used. No `noUnusedLocals` in `tsconfig.base.json`, so typecheck stays green. Does not block.

## Answer to "is the goal loop bounded on every path?"

Every path that reaches a **dispatch** is bounded three ways (`checkRails` before each turn, `reserveIteration` on the way in, `MAX_ITERATIONS = 100` as the un-talkable-out-of backstop). Every path that reaches a **decision failure** is bounded by `stuckCount` via `settleTurn`. The roster-read failure is bounded the same way.

The one unbounded path is `LocalDecisionUnavailableError` (H-1). It spends money only in variants (3) and (4); variants (1) and (2) cost nothing but leave the goal permanently `active` with no stop and no push, which is its own failure of the unattended contract.

## What remains for GO

1. Give the unavailable path a bound of its own — a per-goal consecutive-unavailable counter with a ceiling, stopping with the honest reason ("the local worker has been unavailable for N turns") and a push. Reusing `stuckCount` would re-create M-C; a separate counter would not.
2. Widen the control-plane abort to cover the worker's queue wait (`timeoutMs + DECISION_QUEUE_WAIT_MS + margin`, not `timeoutMs + 5s`), so a decision the worker actually ran is never discarded as "busy, spent nothing".
3. Classify on the worker's own `{busy, retryable}` body and status code rather than `/\b503\b/` over an error string, so an upstream 503 inside a 500 body is not read as availability.
4. Correct `DEPLOY.md:319-323` and `PROGRESS.md:204-209` to match whatever (1)–(3) settle on.
