## HIGH

### H1. Every goal specialist turn dies on the handoff size cap, and the loop retries it forever

`goal-orchestrator.ts:258-261` · `handoffs.service.ts:75-78` · `packages/shared/src/contracts/handoff.ts:34` · `session-consumer.ts:170`

`dispatch()` ends every specialist with `handoffs.ensureForSession(result.sessionId, result.summary || fallback)`. When the agent did not call `agentos_create_handoff` itself — the default — that becomes `createForSession(sessionId, { outcome: <whole session summary> })`. The summary is `lines.join("\n")`: one line per `agent.message` (≤280 chars, `cloud-runner.ts:284`) plus one per tool call (≤200 chars + tool name, `session-consumer.ts:120-131`), with **no ceiling**. `createHandoffSchema.outcome` is `max(4_000)`. Roughly 15 agent messages or 20 tool calls exceeds it — i.e. any real implementation turn.

Chain: `safeParse` fails → `BadRequestException` → `Promise.all` (`goal-orchestrator.ts:170`) rejects → `runClaimedIteration` throws → `runIteration` releases run and lease, rethrows → job fails. The throw is **before** `goal-orchestrator.ts:185-186`, so `recordProgress` never runs and **the stuck rail never advances**. The goal stays `active` with nothing queued until `MaintenanceService.recoverStalledGoals` re-queues it; the next turn evaluates, calls `reserveIteration`, provisions a container, spends real money, and dies at the same line. Repeat.

Only `MAX_ITERATIONS = 100` (`goal-rails.ts:72`) and the spend cap stop it — and a goal with no cap is a supported shape. Stuck-at-19, the rail built for exactly this, is bypassed.

**Blocks unattended use: yes.** This is the failure the rails exist to prevent, on the default path.

The fan-out test (`goals.spec.ts`, "owns bounded parallel specialists") passes only because `FakeRunner` emits a short script; nothing exercises a realistic summary length. Clamping at the call site alone isn't sufficient — failing to record a handoff should not be able to fail the turn.

## MEDIUM

### M2. Removing a recommended skill makes a built-in agent permanently undispatchable — the opposite of the README

`capability.service.ts:85-90,151` · `preflight.ts:113-121` · `README.md`

`cards()` pushes a reason for every `role.recommendedSkills` slug not attached to a built-in agent, and `ready = reasons.length === 0`. `eligibleRoster` filters on `card.ready`, and preflight raises `agent-not-ready` / `no-capable-agent` / `eligible-roster-empty` from the same flag.

So the curation the installer deliberately preserves (`catalog.service.ts:598-625`, `agents.service.ts:207`) is the same act that makes the agent ineligible for every goal and blocks every workflow dispatching to it. Repro: install `minimal-core`, resolve both slots, remove one skill from `senior-dev`, run preflight — fleet blocked, and re-running the installer will not restore it. README says removal is supported "including intentionally making it empty." A *recommendation* is enforced as a hard requirement.

**Blocks unattended use: no** — fails closed and names the reason — but it turns a documented supported action into a dead end, and the doc claim is false as written.

### M3. `local` can bill the metered Anthropic API; the README says it never does

`apps/local-runner/src/decision.ts:48` · `goal-evaluator.ts:124-130` · `README.md`

`runDecision` returns `billingMode: credential.kind === "oauth" ? "subscription" : "metered-api"`. A worker resolved to an API key (a supported config in `config.ts`) bills per token. The evaluator detects it and records `provider = "anthropic-api-via-local-worker"`; the briefing counts `localMeteredSessions` (`briefing.service.ts:59`). So the code knows — but nothing warns at the point of choice, and the README asserts explicit `local` "never the Anthropic API."

Routing itself is correct: `runner-router.ts:100-110` throws rather than falling back, `session-orchestrator.ts:361-366` refuses fallback after a worker refusal, `goal-evaluator.ts:102-109` lets only `auto` degrade. Verified by `goal-evaluator-routing.spec.ts` and `routing.spec.ts`. The gap is billing mode, not backend choice.

**Blocks unattended use: no**, but it undercuts `PRODUCT.md` property 0. Either soften the doc or refuse a metered credential for `local` decisions.

### M4. Explicit `local` routes on `healthy`, not `ready` — a drained worker is picked, then 503s

`runner-router.ts:102` (`healthy`) vs `:118` (`ready`) vs `preflight.service.ts:211` (`ready`)

Preflight blocks explicit local when the worker is not `ready`; routing admits it when merely `healthy`. Press **Drain worker** (`runner-panel.tsx:128`) on a `local`-pinned project and the next session routes to the worker, gets `503 this worker is draining` (`apps/local-runner/src/main.ts:184-190`), and surfaces as a session failure rather than "draining." At-capacity is handled correctly — the request queues FIFO (`capacity.ts:31-49`).

**Blocks unattended use: no** (fails closed, no cloud spend), but drain doesn't do what the panel implies for pinned-local work.
